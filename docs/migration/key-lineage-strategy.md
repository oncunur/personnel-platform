# Migration Key and Lineage Strategy

This document defines how Sprint 16 migration work identifies source records, resolves target references, and remains safe to repeat.

## Core rule

Target GUIDs are generated by the Personnel Platform. Legacy numeric/string identifiers are **not** copied into target primary-key fields unless a target business field explicitly represents that legacy code.

Every migration source record instead receives a stable lineage identity:

`source_system + source_object + source_key`

Example:

`LEGACY_HR | EMPLOYEE | 001245`

That identity must be unique inside a migration run and must resolve deterministically to the same target entity on a repeated dry run.

## Natural business keys

Where available, migration matching should prefer stable business codes rather than display names.

| Domain | Preferred matching key | Notes |
| --- | --- | --- |
| Company | company code | must be unique in agreed scope |
| Branch | company code + branch code | never match by branch name alone |
| Department | company/branch scope + department code | hierarchy must be resolved before employees |
| Position | company scope + position code | names may change over time |
| Project | company scope + project code | preserve inactive/history projects when required |
| Cost center | company scope + cost-center code | required for finance/payroll reconciliation |
| Employee | company scope + personnel/employee number | national identity value may be secondary duplicate-control evidence, not the primary migration key |
| Camp | company/project scope + camp code | verify ownership/scope |
| Room/bed | camp code + room/bed code | load after camp master |
| Meal type | company scope + meal-type code | use value dictionary where source labels differ |
| Document type | company scope + document-type code | binary files need separate checksum lineage |
| Asset | asset/tag/serial code | duplicate serial handling must be explicit |
| Vehicle | plate/VIN depending business rule | normalize plate formatting before matching |
| Integration mapping | integration system + entity type + external code | existing platform constraint should be preserved |

If the source does not have a stable code, MIG-002 must define an explicit deterministic surrogate rule and the business owner must approve it.

## Migration lineage map

MIG-003 should implement a migration-only lineage store (database staging schema or controlled artifact) with at least:

- migration run id
- source system
- source object
- source key
- source row hash
- target entity type
- target entity id
- result status
- error code/message
- migrated at

The lineage store enables:

- idempotent re-runs;
- source-to-target traceability;
- duplicate prevention;
- reconciliation sampling;
- rollback/investigation of individual records.

It must not contain plaintext sensitive values unless absolutely required. Prefer source hashes and identifiers.

## Idempotence rules

1. If a lineage identity already maps to a target entity and the source row hash is unchanged, the row is skipped as already applied.
2. If the lineage identity exists but the source hash changed, the migration rule must explicitly choose UPDATE, REJECT or MANUAL REVIEW. Silent overwrites are prohibited.
3. If a business natural key already exists in target but lineage does not, classify as MATCHED_EXISTING or DUPLICATE_CONFLICT; do not create a second record automatically.
4. Historical transactional records should normally be append-only after successful migration unless the target aggregate explicitly supports correction/versioning.
5. Failed rows remain retryable without reprocessing successful rows.

## Sensitive-data rules

- National identifiers, passport/tax values, IBAN/bank information and salary values must enter the platform through the same encryption-aware application/infrastructure services used by normal application writes.
- Never place plaintext protected values in Git, migration logs, issue bodies, CI artifacts or reconciliation screenshots.
- Reconciliation for sensitive fields should use authorized sample reads, masked representations, hashes where appropriate, and aggregate coverage counts.

## Files and documents

For file migration, lineage must also capture a cryptographic checksum (SHA-256 preferred), source path/object id, target stored-file id and byte size. A successful metadata row with a missing/corrupt binary is a migration failure.

## Date/time normalization

MIG-002 must identify whether each source timestamp is UTC, local time, offset-aware, or date-only. Ambiguous local timestamps must not be guessed. For historical attendance data in particular, timezone/day-boundary rules must be approved before conversion.

## Deletions and inactive records

Legacy soft-deleted/inactive records are not automatically discarded. The source inventory must state whether they are required for historical relationships, payroll/reporting continuity or legal retention. Their target status must be explicit.

## Identity boundary

Legacy authentication material is never migrated as trusted credentials:

- no password-hash copy;
- no refresh-token/session copy;
- no MFA secret/challenge copy.

Users, roles, permissions and scopes are provisioned in the target after access review. `EmployeeUserLink` is created only after both employee migration and target user provisioning are complete.
